# 第四步：让告警与查询在重启后保留

版本0.4.0，M4。仍在同一台Ubuntu中运行，不需要重新装Linux、安装SQLite开发包或创建数据库账号。Windows保存源码；Ubuntu负责C++编译和测试；MobaXterm只是连接Ubuntu的终端。

这一轮新增的效果：上一步停止服务就丢失的设备档案、告警与查询记录，现在保存到本地SQLite文件。服务启动时恢复记录；历史数据不会把设备变成在线。

## 1. 先运行全部自动测试

先在旧A/B终端各按Ctrl+C，停止旧服务和模拟器。更新源码不会自动更新已经运行的进程。

在Ubuntu终端执行：

```sh
cd /home/book/batt-access
sh scripts/test-linux.sh
```

第一次会多编译SQLite和batt-db，最终应看到：

```text
100% tests passed, 0 tests failed out of 6
```

6个测试组：core、query_unit、storage_unit、network、query_network、persistence。测试使用临时库和独立端口，不操作access.db/m4-demo.db。persistence中故意制造的服务异常退出是测试动作，最后所有断言仍须通过。

## 2. 先自动看一遍崩溃恢复

在Linux shell执行：

```sh
python3 scripts/demo-persistence.py
```

脚本自己启动服务和Python模拟客户端，执行以下步骤并逐项断言：

1. BT000登录、上报属性与03告警，完成查询1，再发起查询2，保持pending。
2. 用SIGKILL终止脚本创建的服务，模拟进程崩溃。
3. 使用同一数据库重启：BT000是offline，open告警仍为1，查询1仍success，查询2变成link_lost/server_restart。
4. 终端重新登录、采集并重发03集合；新查询编号继续增长，告警历史仍为1。

正常会依次打印中文步骤，最后出现“全部断言通过”。每次演示使用新临时库，所以这里编号通常为1、2、3；正式手动库应以实际输出为准。脚本只杀自己的服务，结束后清理自己的临时库。

## 3. 用A/B两个窗口自己重启一次

终端A（Linux shell）启动：

```sh
cd /home/book/batt-access
./build/batt-access --db m4-demo.db --quiet
```

首次自动建库；ready中应有milestone=4、persistence=sqlite、sqlite_version=3.51.3及数据库绝对路径。保持A运行。

终端B（另一个SSH会话）启动：

```sh
cd /home/book/batt-access
./build/batt-sim --demo serve --devices 1
```

B出现serving后，在**A正在运行的服务里**逐条输入：

```text
status BT000
alarms BT000
query BT000
```

应看到[STATUS] online_fresh、电压等实时值；alarms出现一条03/open；query先pending后success，随后[RESULT]显示911参数。记下本次编号N，再在A输入 `task N`（把N换成实际数字，例如 `task 1`），应能查到success和结果。持续上报不会刷屏，可用quiet off查看原始JSON。

接着进行正常停止：先在B按Ctrl+C，再在A输入quit。A回到book@100ask的shell提示符后，原样重启：

```sh
./build/batt-access --db m4-demo.db --quiet
```

先不要重启B，在A输入：

```text
status BT000
alarms BT000
```

预期status为offline，电压/电流/SOC/温度显示--；03告警仍为open。在A输入刚才的 `task N`，旧查询仍是success，结果也仍在。

此时在A输入 `query BT000` 会得到新的编号和link_lost，reason=offline，不发910。它表示有设备档案，但当前设备没在线。

再在B运行原来的模拟器命令，回A输入status和query：设备重新fresh，查询成功，新编号比重启前大。同一03告警重发不会新增第二条open。

## 4. 直接查看真正保存的数据

打开第三个SSH终端，或先退出A后在shell执行。不要把以下命令输入服务CLI：

```sh
cd /home/book/batt-access
./build/batt-db -readonly -header -column m4-demo.db "SELECT dev_id,imsi,first_seen_ms,last_login_ms FROM device;"
./build/batt-db -readonly -header -column m4-demo.db "SELECT id,event_no,dev_id,alarm_desc,status,first_ms,last_ms,clear_ms FROM alarm ORDER BY id;"
./build/batt-db -readonly -header -column m4-demo.db "SELECT txn_no,dev_id,status,reason,created_ms,finished_ms FROM query_task ORDER BY txn_no;"
```

时间是UTC Unix毫秒，不是程序启动后的毫秒。batt-db是项目一起编译出来的SQLite命令行工具，-readonly只读查看。不要手工修改正在运行服务的数据库。

## 5. 单独运行故障与恢复验收

```sh
python3 tests/persistence_test.py ./build/batt-access ./build/batt-sim
```

预期19项测试、最后OK。包括事务中途崩溃、COMMIT后未回ACK崩溃、失败回滚、外部写锁占用、pending恢复、自增编号、完整911结果、唯一约束、正常退出和退出超时。部分测试还分多个子场景执行。

需要检测构建时，可分别运行（通常比普通编译慢）：

```sh
BATT_BUILD_DIR=build-asan BATT_SANITIZE=ON sh scripts/test-linux.sh
BATT_BUILD_DIR=build-tsan BATT_THREAD_SANITIZE=ON sh scripts/test-linux.sh
```

TSan的CTest配置仅抑制SQLite官方注明可能误报的walIndexTryHdr共享内存访问；其余代码仍检测。原始失败日志、依据和最终结果见第四步验收记录，不能把这一处抑制解释成SQLite并发行为已完全验证。

## 6. 你需要能解释的三个点

1. 111成功、411成功意味着对应登记/告警事务已提交；311只确认属性在当前进程接纳；任务成功须先保存完整911结果。
2. 数据库COMMIT和TCP ACK不能组成一个事务。提交后ACK丢失可以发生，告警重发按“当前集合”收敛；不能声称所有报文跨崩溃exactly-once。
3. 历史open表示上一次已确认仍活跃的告警，不代表终端当前在线。重启后的pending不能继续等旧连接，必须结束为link_lost/server_restart，再由新会话发新查询。

默认不写--db时使用当前工作目录的access.db；因此教程统一先cd到项目目录。必须保留同一数据库文件才有跨重启记录和编号保证。服务运行期间不要仅复制主db文件当作完整备份，WAL里可能还有已提交内容。

完成前四节后，你就亲手验证了这一轮的持久化闭环；最后F阶段再做整体演示与项目讲解。
