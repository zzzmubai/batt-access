## 2. 独立 Ubuntu 24.04 虚拟机（ISO 路线）

从 [Ubuntu 24.04 官方发布目录](https://releases.ubuntu.com/24.04/)获取 AMD64 live-server ISO，按[官方校验教程](https://ubuntu.com/tutorials/how-to-verify-ubuntu)验证签名与 SHA256。ISO、磁盘和配置放在项目 `.local/` 内，不纳入 Git。

下面先打印创建计划，`IsoSha256` 必须填写经官方校验的实际 64 位校验和：

```powershell
.\scripts\new-v3-vm.ps1 -IsoPath 'ISO绝对路径' -IsoSha256 '实际SHA256' -PlanOnly
```

核对后去掉 `-PlanOnly` 创建独立虚拟机。脚本固定使用项目 `.local/v3-vms/`，配置 4 GiB 内存、2 vCPU、32 GiB 动态磁盘和仅回环 SSH 转发。已有同名机器、目标目录、占用端口或校验和不匹配都会失败；中途失败保留 V3 残留供检查，不自动删除目录或机器。

创建完成不等于安装完成。在 VirtualBox 打开新机器，安装 Ubuntu 24.04，创建 `book` 用户并启用 OpenSSH。安装结束移除安装光盘，确认新系统和旧 `ubuntu` 是不同虚拟机。

本次实际采用较小的官方 [Noble Cloud VMDK](https://cloud-images.ubuntu.com/noble/current/) 和 NoCloud 初始化镜像：

1. 把 `noble-server-cloudimg-amd64.vmdk` 和同批次官方 SHA256SUMS 下载到 `.local/v3-downloads/`，核对校验和。
2. 在**桌面登录用户**的 PowerShell 中准备 Python `pycdlib==1.14.0`、`cryptography`，然后执行 `python scripts/prepare-v3-cloud.py --name v3-cloud-host`。目录已存在时拒绝覆盖；只在私有目录保存新 SSH 身份。
3. 执行云镜像创建预览：

```powershell
.\scripts\new-v3-vm.ps1 `
  -CloudDiskPath '.local\v3-downloads\noble-server-cloudimg-amd64.vmdk' `
  -CloudSha256 '从同批次官方SHA256SUMS取得的64位校验和' `
  -SeedIso '.local\v3-cloud-host\seed.iso' -StartHeadless -PlanOnly
```

核对后去掉 `-PlanOnly`。脚本克隆下载磁盘为单独 VDI、扩容并以 EFI 启动，不把下载原件直接作为运行磁盘。公钥注入专用 `book` 用户，禁用 root/密码 SSH；仅这台开发测试 VM 的 `book` 具有免密 sudo。

```powershell
ssh -p 2224 -i .local/v3-cloud-host/id_ed25519 `
  -o UserKnownHostsFile=.local/v3-cloud-host/known_hosts `
  -o StrictHostKeyChecking=accept-new book@127.0.0.1
```

首次确认主机后后续使用 `StrictHostKeyChecking=yes`。密钥须由运行 VirtualBox/SSH 的同一桌面用户生成；Windows 版准备脚本会调用 `protect-v3-key.ps1` 设置仅当前用户、SYSTEM、管理员可访问的权限。不要为了跨沙箱读取而把私钥开放给 Users/Everyone。

专用云 VM 可使用 `sudo sh scripts/provision-v3-linux.sh` 安装依赖。此安装器检查 Ubuntu 版本、hostname 和固定 NoCloud instance-id，拒绝在旧机或普通未知 Linux 主机执行。它通过 Oracle HTTPS 仓库及独立签名密钥安装 8.4 LTS，检查包候选版本，不绕过 APT 签名验证。

实际云镜像和安装结果见验收记录；本文命令中的 SHA256 必须取自使用的镜像批次，不能拿本次的值套用未来更新的 `current/` 文件。

## 3. 新 Linux 依赖

只在新主机执行，先检查系统：

```sh
. /etc/os-release
test "$ID" = ubuntu && test "$VERSION_ID" = 24.04
sudo apt-get update
sudo apt-get install build-essential cmake pkg-config python3-venv openssh-server ca-certificates libssl-dev zlib1g-dev libzstd-dev
```

数据库要求 **Oracle MySQL 8.4 LTS 与同系列 C API**。不要直接把发行版默认 MySQL 或 MariaDB 当成已验证的 8.4 环境。按 [Oracle MySQL APT 仓库教程](https://dev.mysql.com/doc/mysql-apt-repo-quick-guide/en/)安装当前仓库配置包，选择 8.4 LTS，然后检查候选包：

```sh
sudo apt-get update
apt-cache policy mysql-server libmysqlclient-dev
```

确认候选版本均属 8.4 后安装：

```sh
sudo apt-get install mysql-server libmysqlclient-dev
mysql_config --version
mysql --version
```

在 MySQL 的实际配置中保持只监听回环地址，核对 `innodb_flush_log_at_trx_commit=1`；启用 binlog 时记录 `sync_binlog` 实际值。准入程序会打印这些非敏感配置，未把断电持久性当作本次已验证能力。

## 4. 专用 M0 库和凭据

在新主机使用交互式管理员会话建库、建账号；密码只在新主机私有配置中保存，不传入 shell 参数或 Git。以下密码是说明占位值，执行前在私有会话内替换：

```sql
CREATE DATABASE batt_test_m0 CHARACTER SET utf8mb4;
CREATE USER 'batt_m0'@'127.0.0.1' IDENTIFIED BY '替换为本机生成的测试密码';
GRANT CREATE TEMPORARY TABLES ON batt_test_m0.* TO 'batt_m0'@'127.0.0.1';
```

没有 `IF NOT EXISTS`：同名已有库/账号应当检查来源，不自动复用未知数据。此账号只用于 M0 临时表；M1 的初始化账号和 M3 的运行账号之后另设。

```sh
cd /home/book/batt-access-v3
mkdir -p .local /home/book/batt-v3-runtime
chmod 700 .local /home/book/batt-v3-runtime
cp config/mysql-m0.example.ini .local/mysql-m0.ini
chmod 600 .local/mysql-m0.ini
```

用编辑器填写 `.local/mysql-m0.ini` 的实际密码。格式为单个 `[mysql]` 段；值首尾空白被去除，不支持引号转义和行内注释，密码中间的 `#`、`;`、`%`、`=` 均按字面值处理。

专用云 VM 也可以运行 `sudo python3 scripts/create-m0-fixture.py`，在新库中生成随机账号密码和受保护配置。这个一次性工具只对固定 instance-id 生效，不输出密码，已有配置或 SQL 冲突时拒绝继续，也不自动清理残留；不要与上述手工建库流程重复执行。

建立独立 Python 虚拟环境：

```sh
python3 -m venv .local/venv
. .local/venv/bin/activate
python -m pip install --upgrade pip
python -m pip install --index-url https://pypi.org/simple -r tools/m0/requirements.txt
python -m pip list --format=freeze > .local/m0-python-resolved.txt
```

PyMySQL 及 RSA 认证依赖已在本次 M0 实测并固定，完整版本见 `requirements.txt` 和验收记录。初始解析失败时不要禁用认证或放宽断言；先检查 pip 版本和官方索引可用性。

## 5. Linux M0 一键检查

每次使用新的证据目录：

```sh
. .local/venv/bin/activate
mkdir -p artifacts
sh scripts/check-v3-m0.sh \
  /home/book/batt-access-v3/.local/mysql-m0.ini \
  /home/book/batt-access-v3/artifacts/m0-001
```

脚本顺序执行系统清单、独立 CMake 构建、配置保护测试、C API 小程序和独立 Python 驱动。任何一步失败即非零退出，已有证据目录不覆盖。`inventory_ready` 只表示依赖检查满足，不等于 M0 已通过。

C API 程序验证参数绑定、包含 NUL 的字节串、SQL NULL、超过 2^53 的整数、提交、显式回滚和异常展开回滚。只创建连接级临时表；DDL 不参与业务事务。析构顺序为语句/结果集 → 连接 → 全局客户端库。失败仅报告操作名和错误码，不打印 MySQL 原始错误、账号或连接串；COMMIT 失败明确提示结果可能未知，不重放事务。

Python 程序使用独立驱动验证临时表中的整数/二进制/NULL 和回滚。它不是将来 Store 业务回归的替代品；M4 仍需独立连接读取真实业务记录。

## 6. Windows Qt 6 准入

安装官方 Qt 6 开发套件和该 Qt 版本配套的编译器，包含 Widgets、Network、Test 和 CMake/Ninja。现有 Anaconda Qt 5.15.2 不满足要求。按[官方 Windows 工具链说明](https://doc.qt.io/qt-6/windows.html)匹配版本，不混用现有 MinGW 13.2 与任意 Qt 二进制包。

在所选 Qt 套件的开发命令行执行：

```powershell
cmake -S tools/m0/qt -B build-qt-m0 -G Ninja -DCMAKE_PREFIX_PATH='你的Qt6套件目录'
cmake --build build-qt-m0
ctest --test-dir build-qt-m0 --output-on-failure
.\build-qt-m0\qt_smoke.exe
```

最小窗口只验证异步 GET，不是完整 Qt 运维客户端。自动测试包含本机假 HTTP 慢响应、GUI 定时器推进、请求期限、关闭中的 reply 释放，以及 `9007199254740993` 和 INT64_MAX 的 JSON 整数往返。请求只允许无凭据的 `http://127.0.0.1`，不自动跟随重定向。

状态刷新、同号重试、任务轮询、告警分页和 generation 保护属于 M5，不能由此小窗口宣称已完成。

Windows 含中文路径时，本次 MinGW Makefiles 生成器构建失败，Ninja 已通过配置保护程序构建；后续教程统一使用 Ninja。

安装器 aqtinstall 3.3.0 也遇到中文路径解码错误。本次尝试把项目 `.local` 映射为 `Q:` 再安装：只有空闲盘符才允许映射，不覆盖已有盘符。映射是当前 Windows 用户会话状态，重启后需要重新建立；对应真实文件仍在忽略目录。Qt 和编译器路径必须在同一开发环境中配置，实际成功版本以验收记录为准。

**实际验证后的方案**：工具链和源码快照都使用英文真实路径。Qt 6.8.3 与 MinGW 13.1.0 已安装在 `E:\batt-v3-tools`；运行以下脚本会创建新的源码快照，逐文件核对 SHA256，在该英文目录构建，并在项目 `artifacts/qt-m0-<id>/` 保存日志和 summary。中文路径主源码仍为编辑入口。

```powershell
.\scripts\build-v3-qt-m0.ps1 `
  -CMake '你的cmake.exe绝对路径' `
  -Ninja '你的ninja.exe绝对路径'
```

`summary.json` 给出可运行 `qt_smoke.exe` 的 build 目录；运行时把 `E:\batt-v3-tools\6.8.3\mingw_64\bin` 和 `E:\batt-v3-tools\Tools\mingw1310_64\bin` 加入当前进程 PATH。此小窗口只用于 M0，不代替 M5 运维客户端。

## 9. V3.1 日常构建、运行及 Qt

在新 Ubuntu 创建独立正常业务库、初始化账号与运行账号。初始化账号在指定库有 DDL 权限；运行账号仅 SELECT/INSERT/UPDATE/DELETE。不要复用旧 SQLite，也不要给运行账号建库/删库权限。两个私有 INI 均按 `config/mysql.example.ini` 格式填写，权限 600；创建固定 runtime_dir，权限 700。

```sh
cd /home/book/batt-access-v3
. .local/venv/bin/activate
sh scripts/init-mysql.sh --db-config /absolute/private/initializer.ini
cmake -S . -B build-v3 -DCMAKE_BUILD_TYPE=Debug
cmake --build build-v3 -j2
./build-v3/batt-access --db-config /absolute/private/runtime.ini --http-port 19002
```

另一个终端运行 `./build-v3/batt-sim --demo serve --devices 1`。首台设备为 BT000。

独立测试使用专用账号，不用正常业务库：

```sh
export BATT_MYSQL_TEST_CONFIG=/home/book/batt-access-v3/.local/mysql-test-admin.json
sh scripts/test-mysql.sh
python scripts/demo-http.py --build-dir build-v3 --output-dir artifacts/http-new-run
```

Debug、ASan 和 TSan 必须分别使用构建目录。该虚拟机 TSan 需仅对测试进程关闭 ASLR：

```sh
cmake -S . -B build-v3-tsan -DCMAKE_BUILD_TYPE=Debug -DBATT_THREAD_SANITIZE=ON
cmake --build build-v3-tsan -j2
setarch x86_64 -R ctest --test-dir build-v3-tsan --output-on-failure
```

没有修改系统级 ASLR 或增加 suppression。MySQL 服务与预编译客户端库的检测边界见验收记录。

Windows 在项目目录构建客户端：

```powershell
.\scripts\build-qt-client.ps1 `
  -CMake 'E:\Visual_Studio_2026\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe' `
  -Ninja 'E:\Visual_Studio_2026\Common7\IDE\CommonExtensions\Microsoft\CMake\Ninja\ninja.exe'
```

脚本的 summary 给出实际 build 目录。再执行 `.\scripts\package-qt-client.ps1 -Build '实际build目录'` 收集 DLL/平台插件/编译器运行时并自检，生成本地 ZIP。解压整个目录后运行 `batt-ops.exe`；不要只复制 EXE。目录和 ZIP 位于忽略的 `artifacts/`，源码上传 GitHub，真实账号和构建产物不入 Git。

先打开 SSH 隧道（新 VM 的 SSH 端口是 2224）：

```powershell
ssh -p 2224 -i .local/v3-cloud-host/id_ed25519 `
  -o UserKnownHostsFile=.local/v3-cloud-host/known_hosts `
  -o StrictHostKeyChecking=yes -N -L 127.0.0.1:19002:127.0.0.1:19002 book@127.0.0.1
```

保持隧道进程运行。Qt 地址填 `http://127.0.0.1:19002`，设备填 BT000。

- 状态页：手动读取或自动刷新，默认 2 秒。同类请求最多一条在途，显示四项属性及最旧属性年龄；请求失败时旧值明确标记。年龄来源于服务端内存采样时刻，不是历史数据库。
- 查询页：新建后显示请求号/任务号；201 表示任务已创建。pending 每 500ms 轮询，最多观察 10 秒；观察超时不改写服务端状态。传输失败或 503/unknown 保留原号，点击同号恢复；已知任务号优先 GET。
- 告警页：全部/open/cleared、重置第一页、下一页；末页停止。换设备/地址/筛选会清空当前页，晚到响应不能覆盖新页面。

请求号恢复上下文只在当前应用进程内保存。若关闭客户端前结果未知，请先复制请求号，重启后可按 HTTP 教程用原号恢复；本版没有持久化未决请求台账。Qt 设置只保存地址、设备和周期，不保存 MySQL/SSH 密码。

真实自动联调入口：`scripts/test-qt-live.py --qt-build <实际build> --output <新的证据目录>`；它启动自己拥有的服务、模拟器和临时 SSH 隧道，结束后清理。固定示例中的正常业务服务不会被它停止。
