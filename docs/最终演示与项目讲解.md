## 4. 这个项目到底是什么

它是一个Linux/C++设备接入与运维服务的个人拓展实现：接收多台模拟电池终端的数据，为每台设备维护当前会话、属性新鲜度、告警生命周期和只读参数查询；服务重启后恢复已确认的告警与查询记录。

原实习终端通过MQTT或TCP上传已有用途。本项目的范围是独立实现并验证服务端接入、并发与恢复，不宣称替代企业原平台，也不虚构企业需要这套系统。你能证明的是：给定这套协议，自己理解并能维护一个有会话隔离、事务语义和故障测试的接入后端。

核心技术与代码对应：

| 技术 | 本项目中具体做了什么 | 阅读入口 |
| --- | --- | --- |
| 非阻塞socket/epoll | 一条I/O线程管理多连接、残帧、短写、关闭与CLI | src/access.cpp、src/json_slice.hpp、src/send_buffer.hpp |
| 工作线程与条件变量 | devId固定分片，同设备顺序执行；有界队列，满时断开式卸载 | src/worker.cpp、src/bounded_queue.hpp |
| 查询状态与超时 | 单调时钟期限、关联设备/会话/编号、迟到不翻案 | src/query_task.hpp |
| SQLite C API | 参数绑定、事务、先提交后成功、AUTOINCREMENT、启动恢复 | src/store.cpp |
| 验证 | 独立报文、真实TCP、SQL错误、提交边界崩溃与检测构建 | tests、docs/test-results |

现有代码没有通用线程池：两个固定worker执行对应分片业务。它们能隔离不同分片的慢业务，SQLite写事务仍串行。不能将其描述成通用任务调度框架或并行写库性能优化。

简历表述可按实际理解程度使用：

> 电池终端接入与运维服务（个人Linux/C++项目）：参考实习协议独立实现多连接TCP接入，使用epoll、固定设备分片与有界队列维护会话和查询状态；通过SQLite事务实现告警/任务持久化与重启恢复，完成32模拟终端、迟到响应及提交边界崩溃测试。

不要写企业上线、真实设备规模、未知QPS或手写通用线程池。跑通是验收，能解释并修改代码才是你在面试中可展示的能力。

## 5. 接下来读懂三个闭环

1. 在A输入query BT000，沿access.cpp的dispatch_command→worker.cpp的command→Queries::begin→Store::create_query，直到I/O发出910；再跟踪911如何提交success。自己画出线程与消息流。
2. 跟踪新连接110替换旧连接：fd为何不足以识别连接、旧关闭通知如何被过滤、旧pending如何与新登记一起提交。用最终演示第4段对照。
3. 跟踪410的候选缓存、BEGIN/COMMIT、411输出，再看失败和重启恢复。解释为什么提交后ACK仍可能丢失，以及为什么重启后告警保留但设备offline。

先把这三个闭环讲清，再决定是否拓展HTTP、通用线程池或其他存储。第一版验收完成，不意味着需要立刻继续堆技术栈。
