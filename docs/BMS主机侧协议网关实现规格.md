# 电池终端接入与运维服务：实现规格

> 修订版：2026-10-19。个人拓展项目，主线为 Linux/C++ 系统与网络编程，兼顾设备接入服务端开发。
> 业务与基础报文字段参考实习项目的 `ElectricalCabinetComm.py`、`ElectricalCabinetHandler.py`。本项目独立实现服务端与模拟终端，不修改原终端，不依赖原企业平台或生产数据。
> 本文替代旧版“BMS 主机侧协议网关”及上一版接入服务规格。文件名保留以便继续引用。
> 本文是设计与验收目标，不代表功能已经实现。模拟测试、真实硬件联调、生产运行三类证据必须分别说明。

## 1. 业务目标与项目边界

原终端负责采集并上传电池数据；本项目负责接收一批终端的数据，维护设备会话、数据新鲜度、告警生命周期和只读运维查询任务。

服务需要回答：

1. 哪些设备已连接但尚未登录，哪些已登录且数据有效，哪些数据过期，哪些已断开？
2. 持续上报的同一告警怎样合并，恢复后再次触发怎样形成新的事件？
3. 参数查询何时被受理、发送、完成、超时或因连接丢失结束？
4. 连接替换、fd 复用、迟到响应和重复响应是否会污染当前会话？
5. 服务重启后，已提交的告警和任务能否恢复？
6. 慢任务、慢接收端和数据库失败时，系统是否保持有界资源占用及明确的失败行为？

第一版不承诺判断电池真实健康状况、执行充放电安全控制、识别现场故障根因，也不声称已经生产部署。参数阈值和连续电池数值用于模拟业务，不用于论证电池算法准确性。

## 2. 技术范围与分阶段交付

技术基线：C++17、Linux POSIX socket、非阻塞 I/O、epoll 水平触发（LT）、标准库线程与有界队列、SQLite 官方 C API、成熟 JSON 库，例如固定版本的 nlohmann/json。依赖版本和离线获取方法写入 README。

| 阶段 | 必须交付 | 范围控制 |
| --- | --- | --- |
| M1：协议与单设备 | JSON 增量切分、登录、属性、协议固定样例和错误输入测试 | 先证明字节流与业务字段正确 |
| M2：多设备与并发 | 可配置连接数、连接身份、固定设备分片工作线程、有界队列与背压 | 默认 2 个工作线程，支持以 1 个线程对照 |
| M3：业务与持久化 | 告警集合处理、查询任务、数据库事务、启动恢复 | 把已确认成功的关键状态保存下来 |
| M4：验证与交付 | 故障脚本、阶梯负载、退出与崩溃恢复、验证报告 | 报告实测数据和限制，不预填“高并发”成果 |

第一版暂不实现 Redis、MySQL、RPC、HTTP 服务、网页、MQTT、串口 105/141 字节解析和写参数/远控指令。它们是后续需求选项，不是判断项目是否属于服务端的标准。

工作线程使用项目需要的固定分片执行模型，不先建设可承接任意业务的通用任务框架。保留线程创建、队列、停止和统计的必要封装，禁止用“不能封装”妨碍清晰实现。

## 3. 进程、线程及状态所有权

### 3.1 进程

两个可执行程序：`batt-access` 接入服务、`batt-sim` 终端模拟器。测试负责启动和停止它们。第一版不另写 supervisor；崩溃恢复测试由测试驱动重新启动服务，不宣称程序内有自动拉起功能。

### 3.2 线程

```text
batt-access
  I/O 线程（主线程）
    accept / recv / JSON 切分及基础字段解析 / 非阻塞 send
    独占 fd、epoll 注册、每连接接收缓冲和发送缓冲
    向所属分片入队业务事件，接收工作线程返回的有界命令
  N 个分片工作线程（默认 N=2，运行期间不变）
    同一 devId 始终映射到同一分片
    独占本分片设备状态、告警缓存、查询任务与业务定时器
    各自持有 SQLite 连接，事务写入受一把公共写锁约束
```

| 状态或资源 | 唯一修改者 | 跨线程交互方式 |
| --- | --- | --- |
| fd、connection_id 注册表、epoll、收发缓冲 | I/O 线程 | 工作线程只提交携带 connection_id 的发送/绑定/关闭命令 |
| 设备当前会话、属性及时间、open 告警、pending 任务 | 所属分片工作线程 | I/O 投递登录、消息、断开、运维命令；不直接读取业务容器 |
| SQLite 连接与 prepared statement | 创建它的工作线程 | 不跨线程使用 statement；写事务持公共写锁 |
| 工作队列、返回命令队列 | 队列生产者与消费者 | 队列自己的互斥量、条件变量和字节计数 |
| 跨线程指标 | 指标实现 | 原子计数或发送快照，不无锁读取普通 map |

允许 I/O 解析 JSON 和检查基础信封字段，以获取未登录连接的 `devId`。I/O 不做告警判断，不修改任务状态，不调用 SQLite，不等待数据库或工作线程空闲。

分片函数实现为明确的稳定字符串哈希取模 `N`；记录算法。N 在运行中不能更改。不是空闲线程抢任务的模型；同一分片中的其他设备也会受到慢任务影响。

工作线程返回命令后用 `eventfd` 唤醒 I/O。返回队列有界，等待时不能持队列外的业务锁或数据库写锁；关闭时必须唤醒所有等待者。不得向已销毁的 I/O 对象回调。

## 4. 连接身份、事件顺序与时间

### 4.1 connection_id

每次 `accept` 分配 `connection_id = boot_id + counter`，它是独立于 fd 的标识。`boot_id` 每次服务启动重新生成，counter 在该次运行中递增。fd 只用于实际系统调用，不能作为任务或会话的唯一身份。

业务事件、发送命令、绑定命令、关闭命令和断开通知都携带 connection_id。epoll 的用户数据也应能定位到连接身份；处理一批就绪事件时仍要检查连接是否存活。旧事件不能操作被复用的 fd。

### 4.2 业务事件

`Login`、`Attributes`、`AlarmSnapshot`、`QueryResponse`、`QueryCommand`、`Disconnected`、`StatusCommand` 只由 I/O 接入层投递给所属分片。每条队列 FIFO，不允许同一设备同时由两个工作线程处理。

队列接纳事件时，在队列锁内分配 `event_seq` 并记录 `admitted_mono`（单调时钟）和 `observed_wall_ms`（服务端 UTC Unix 毫秒）。入队失败不分配成功接纳时间；留在接收缓冲中的报文尚未被业务层受理。

队列接纳时间不等于数据到达网卡或内核的时间。因背压迟迟未被受理的响应可能超时，这属于第一版明确的端到端预算，不能称为“按网络到达时间判断”。

### 4.3 计时原则

所有等待、数据年龄、查询期限、登录/半帧/发送期限用 `steady_clock`。数据库和展示使用 UTC Unix 毫秒。终端 `alarmTime` 是来源信息，不用于服务器超时与业务排序。

系统墙上时钟跳变不得导致超时延长、提前或在线状态反转。不得把本次运行的单调时钟值加载为下次运行的截止点。

## 5. TCP 字节流、JSON 与报文边界

### 5.1 增量切分

线上仍使用连续 JSON 对象，无换行、无长度头；参考原 `_compact_json` 的发送行为。顶层只接受对象。每个连接独立维护切分状态：对象深度、字符串内外、转义状态、待处理字节。

- 对象外只允许 JSON 空白；其他前缀字节视为协议错误并断开，不扫描到下一个 `{` 后假装已恢复。
- 字符串内的 `{`、`}` 不计数。正确处理转义引号和连续反斜杠，状态跨 `recv` 保留。
- 找到完整对象后交给成熟 JSON 库校验语法、UTF-8、数字和结构；字符串中包含括号不构成分界。
- 即使已经配平，单对象超过 64 KiB 也拒绝；嵌套对象/数组深度上限 64。深度限制由扫描器或库的 SAX/解析回调在深度增长时执行，不能等无界递归结束后再检查。
- 已配平且未破坏字符串边界的坏对象，例如 `{"msgType":310,}`，计 `bad_json` 并丢弃该段；其后正常对象仍可处理。
- 未闭合对象或字符串不能保证重新同步。自对象首字节起 5 秒未完成，或达到大小/深度限制，关闭连接并记录对应原因。不得靠猜下一个 `{` 保证恢复。
- 第一版每连接连续 3 个已配平语法错误即断开；收到合法对象后清零连续错误数，累计错误计数不清零。

报文总长、数组项数和接收缓冲都有限额。扫描器保存当前位置，不得每收到一个字节就从头重新扫描全部缓存。

### 5.2 JSON 语法与业务类型

JSON 库支持完整值类型，未知字段允许出现浮点数、布尔、null、数组或对象；业务选择性忽略。原终端含浮点经纬度，不能因第一版不使用经纬度就拒绝整个报文。

已使用字段按下表校验；整数不能用布尔、数字字符串或小数冒充，转换前检查范围。标识字符串最大 64 字节，devId 非空；txnNo 使用有符号 64 位正整数。业务使用的对象遇到重复键拒绝，不依赖 JSON 库“最后一个键覆盖”的默认行为。

| 方向 | msgType | 字段与行为 |
| --- | --- | --- |
| 终端→服务 | 110 | `devId`、`imsi` 为字符串；`txnNo` 为正整数；`devType=1`。校验和设备登记提交后才登录成功 |
| 服务→终端 | 111 | 回显 `devId`、`txnNo`；成功 `result=1`，可关联的登录失败 `result=0` |
| 终端→服务 | 310 | `devId`、`txnNo`、`attrList`；处理已登录当前连接上的合法属性 |
| 服务→终端 | 311 | 回显 `devId`、`txnNo`，成功 `result=1`；仅代表属性已被内存接纳 |
| 终端→服务 | 410 | `devId`、`txnNo`、`alarmList`；按第 8 节当前集合语义处理 |
| 服务→终端 | 411 | 回显 `devId`、`txnNo`，告警事务提交后成功 `result=1` |
| 服务→终端 | 910 | `devId`、服务端分配的 `txnNo`；只读保护参数查询 |
| 终端→服务 | 911 | `devId`、`txnNo`；`attrList` 可缺省，有则必须是格式合法的数组 |

合法但第一版不支持的 msgType 仅计数，不改变状态。缺少路由字段、字段类型错误、未登录上报、devId 与连接绑定不符，不修改业务状态，不回复成功。回复内容必须由 JSON 库生成，不能拼接未转义字符串。

终端上报中的 txnNo 可能来自秒级时钟，310 和 410 甚至可能共用数值。它不是全局唯一事件号；不能简单用 `(devId, txnNo)` 对所有消息统一去重。服务端查询编号由数据库生成，规则见第 9 节。

## 6. 登录、连接替换与设备状态

### 6.1 登录流程

未登录连接只能提交一条在途 110。校验期间暂停该连接后续业务报文分派，已读取的流水线数据留在有界接收缓冲中。登录成功后再按原顺序处理；失败则丢弃后续业务并关闭。连接 5 秒仍未完成登录则关闭。

I/O 只根据基础信封把 110 路由至分片。工作线程校验完整字段、提交设备登记事务后，才把该 connection_id 设为当前会话，并返回激活命令。I/O 检查该连接仍存活后绑定身份、排队 111 并恢复读取。

无效新登录不能踢掉现有合法连接。成功替换时，同一事务将该设备旧会话 pending 查询结束为 `link_lost/replaced`；提交后业务状态切到新 connection_id，I/O 再关闭旧连接。

旧连接的后续属性、告警、911、关闭通知和尚未发送的命令，均不能修改/关闭新会话。旧连接对应的任务在替换前已完成处理者视为当时有效；替换生效后才处理的旧任务必须丢弃。

一个连接不能在登录后更换 devId；再次以同 devId 发 110，字段合法时幂等回复，不重新建会话、不终止当前查询。相同 devId 的另一条新连接登录才执行替换。

### 6.2 属性与新鲜度

| 属性 id | 含义 | 第一版校验与换算 |
| --- | --- | --- |
| `01111001` | 总电压 | 非负 int32，除以 100 得 V |
| `01112001` | 总电流 | int32，可负，除以 100 得 A |
| `01113001` | SOC | 整数 0—100 |
| `01119001` | 电芯温度 | int32，单位摄氏度 |

同一帧中已使用 id 重复、已使用值非法，整帧拒绝，不做部分更新、不回成功。合法未知 id 忽略；`attrList` 最多 256 项。

允许合法的部分属性上报，但分别维护四个字段的有效标志及接纳时刻。只有至少一个受支持字段更新才算有效属性事件；仅含未知 id 不刷新数据年龄。快照在所属工作线程整份构造，跨线程只发送拷贝。

设备状态：

- `connected_unauthed`：连接已建立但未登录，仅接入层统计。
- `connected_no_data`：已登录，四个字段尚未全部获得。
- `online_fresh`：当前连接有效，四字段都有值，最老字段年龄不超过 90 秒。
- `connected_stale`：当前连接有效且四字段曾齐全，但至少一个字段超过 90 秒。
- `offline`：无当前有效连接。设备档案与历史记录保留。

新连接登录后旧属性只可作为带时间的历史展示，不继承为新连接的新鲜值。参数查询第一版只对 `online_fresh` 受理，其他状态返回明确原因。

## 7. 有界队列、背压与发送

默认限额全部可配置并打印到启动日志；不能只限制业务队列而放任其他缓冲增长。

| 项目 | 默认上限 |
| --- | --- |
| 活连接数（含未登录） | 1024；默认演示仅 32 |
| 单个 JSON 对象 | 64 KiB |
| 每连接接收缓冲 | 256 KiB，包括待入队完整对象和残帧 |
| 每连接发送缓冲 | 256 KiB，包括短写剩余字节 |
| 每分片业务队列 | 64 个事件，且合计载荷不超过 4 MiB |
| 工作线程到 I/O 的返回队列 | 合计 128 个命令，且载荷不超过 8 MiB |
| 全服务接收、任务、返回及发送载荷 | 合计 128 MiB；同一底层缓冲不重复计数 |

1. 队列达到任一上限，I/O 使用 `EPOLL_CTL_MOD` 暂停该连接的 `EPOLLIN`，保留必要的挂断/错误处理和有发送数据时的 `EPOLLOUT`。不得用 DEL 模拟“只暂停读”。
2. 已切出但不能入队的对象留在原连接接收缓冲中，最多维护一个当前待提交对象；不继续解析出无界临时列表。队列降至 32 个且字节占用低于一半时，工作线程通知 I/O 重试。
3. 恢复时先尝试提交已有完整对象，再恢复读取。恢复候选连接轮转处理，单次有处理预算，不让一个终端占满整个 I/O 循环。
4. 全局载荷达到上限时拒绝新增连接并暂停新增业务读取。继续处理发送、队列排空和关闭；现有连接仍不能突破单连接上限。持续无法推进则按登录、帧或发送期限关闭具体连接并计原因。
5. CLI 队列满时立即返回 `busy`。断开通知不能静默丢弃：I/O 每连接保留至多一条待投递关闭通知，连接记录到通知交付前保留；数量由活连接/待关闭记录总上限约束，达到上限拒绝 accept。相同连接不重复积累通知。

所有发送由 I/O 执行：处理短写、EINTR、EAGAIN/EWOULDBLOCK、EPIPE 和 ECONNRESET；忽略 SIGPIPE 或使用 MSG_NOSIGNAL。发送队列非空时关注 EPOLLOUT，空时移除，避免空转。

每次执行发送命令前检查 connection_id 仍有效；旧 fd 数字复用不能改变判断。返回队列满可让工作线程进行可中断等待，I/O 不可等待工作线程。

发送缓冲超限或连续 5 秒无发送进展，关闭该连接并投递断开事件，不静默丢弃已确认的持久化状态。ACK 未发送成功不等于数据库回滚；重连重发仍需业务幂等处理。

## 8. 告警集合与事件生命周期

### 8.1 与原终端的兼容边界

第一版采用 `ElectricalCabinetHandler` 周期上报路径的“当前活跃告警集合”模式：指定组包含当前所有活跃项；无告警时发送 `alarmDesc="000", alarmFlag=0`。不能把它误写成“每项一定单独发恢复事件”。

原代码也有单条告警发送辅助函数，线上无法仅凭相同 410 类型可靠识别“集合快照”或“增量事件”。因此本文明确只对上述周期集合路径负责，不宣称兼容所有原调用方式。增量事件模式如以后增加，必须由配置或协议字段明确选择，不能自动猜测。

只处理 `id="01003001"` 的以下项：

| alarmDesc | 含义 |
| --- | --- |
| `01` | 单芯过压 |
| `03` | 电芯高温 |
| `06` | 压差过大 |

### 8.2 集合处理

- 410 未包含该 id 的任何项：不改变该组，不因组缺席推断全部恢复。
- 包含该组：`flag=1` 的描述组成活跃集合；未知描述不入本服务的已使用集合。每组最多 64 项，重复描述拒绝。
- 该组出现 `000/0` 表示集合为空；它与同组活跃项同时出现为矛盾报文，整帧拒绝。
- 第一版不接受已使用描述的单项 `flag=0`；模拟器的 `alarm <devId> <desc> 0` 是移除本地集合中的该项，再发送完整集合，线上仍遵守集合模式。
- 本帧结构或已使用项非法，整帧拒绝，不先更新一半。未知告警组可忽略，但完整帧仍需合法。

事件键为 `(devId, alarm_id, alarm_desc)`。新集合与本地已提交 open 集合做差：新增项插入 open；持续项更新 last_ms；消失项改为 cleared 并填写 clear_ms；没有 open 的恢复不产生新行；恢复后再触发新建事件。

一帧告警的全部变更在同一事务内提交；提交后才替换 open 缓存并排队 411 成功应答。first_ms、last_ms、clear_ms 使用服务端观察时间，终端 alarmTime 仅按需保留为来源信息。

## 9. 运维入口与只读查询任务

### 9.1 CLI

支持 `devices`、`status <devId>`、`query <devId>`、`task <txnNo>`、`alarms <devId>`、`stats`、`quit`。业务查询也路由给所属工作线程，I/O 不直接读取工作线程容器。

交互终端/管道 stdin 使用非阻塞读取和行缓冲，可加入 epoll；EOF 后取消关注，不能忙循环。对不支持 epoll 的普通重定向文件，命令行支持 `--commands <file>` 在启动监听前读入有界命令清单，监听启动后逐条分派；不得假设任意 stdin 都能 EPOLL_CTL_ADD。

### 9.2 状态和编号

持久状态为 `pending`、`success`、`timeout`、`link_lost`，终态不可反转；reason 记录 offline、stale、replaced、send_error、server_shutdown、server_restart 等原因。队列 busy、非法命令或数据库不可写表示“未受理”，不伪造 pending。

同一 devId 至多一个 pending。重复 query 返回 busy，不覆盖原任务。编号来自 `query_task.txn_no INTEGER PRIMARY KEY AUTOINCREMENT`，在事务内分配，提交后才能发到线上；不在内存从 1 重新计数。使用正的有符号 64 位整数，不使用浮点转换。保留数据库才能保证编号历史不复用，删库即新实验，必须记录。

### 9.3 受理、发送、截止与响应

1. CLI 命令成功入分片队列时记录 t0；查询预算为端到端 3 秒，截止点 `deadline=t0+3s`，包含排队、数据库提交与发送等待。该选择便于实现与测量，不声称是“终端收到后 3 秒”。
2. 工作线程处理命令：设备档案不存在则返回 not_found，不创建带无效外键的任务；已有档案但 offline、stale、no_data 时，写入终态 link_lost 及 reason，不发 910；已经过期则直接持久化 timeout；否则先提交 pending 行并绑定当前 connection_id，再向 I/O 提交携带 deadline 的 910。
3. I/O 在截止点前才开始或继续发送查询；过期且尚未发送则撤销该命令。若仅发送了部分 JSON 后过期，关闭连接，不能截断该对象后继续拼接下一对象。发送完成可回报诊断事件，不延长截止点。
4. 911 只有 devId、当前 connection_id 和 txnNo 全部匹配才有资格完成任务。缺省 attrList 允许表示成功但结果为空；有 attrList 时存储合法数组及原响应 JSON。
5. 工作线程按事件接纳时间与业务截止点合并排序：队首事件的 admitted_mono 小于 deadline，先处理该事件；大于等于 deadline，先推进对应到期任务。队列空时用 condition_variable.wait_until 等待最近截止点，不用 sleep 轮询。
6. 队列的入队时间记录与“空队列已到期”判断必须由同一队列互斥量协调，避免先记录时间、过期处理后才插入事件。2.9 秒已入队但 3.2 秒才处理的合法响应仍可成功；3.1 秒才入队者不能成功。背压期间留在缓冲里的响应不算已入队。
7. 成功结果更新使用事务及 `WHERE status='pending'`；提交后才改缓存。超时、断开或替换也由相同工作线程串行提交，先完成的有效终态不被后续事件覆盖。
8. timeout 后的同 txnNo 应答计 late_frames；按 txnNo 去重的 late_tasks 单独计数。success 后的重复响应计 duplicate_response；link_lost 后响应计 orphan_response；不能修改任何终态。

pending 只表示服务器已持久化并计划发送，不证明终端已收到；send 成功也不证明对端业务执行。没有独立接收确认报文时，不能在 CLI 宣称“终端已确认收到”，只能展示本地发送与最终响应证据。

## 10. SQLite、应答与恢复

### 10.1 连接和事务

启动恢复完成前不监听业务端口。初始化连接创建表、执行恢复后关闭；每个工作线程再创建自己的 SQLite 连接和 prepared statement，使用 `SQLITE_OPEN_FULLMUTEX`。连接开关和所有 SQL 均不在正在运行的 epoll 线程中执行；初始化阶段主线程不算运行中的 I/O 事件循环。

数据库使用本地文件，启用并核实 `journal_mode=WAL`、`synchronous=FULL`、`foreign_keys=ON`；每连接设置有限 busy 等待。写事务持公共进程内写锁，范围从 BEGIN 到 COMMIT/ROLLBACK，完成后释放。不能持该锁等待 socket、返回队列或其他工作线程。SQLite 同时只有一个写事务，不宣称两个工作线程带来并行写库。

锁获取、busy 等待与应用层重试均有总预算，常规默认 500 ms；使用支持有期限获取的写锁，停止时可中断等待。FULLMUTEX 保护 SQLite API 使用，不替代业务原子性。

### 10.2 表结构

```sql
CREATE TABLE device (
  dev_id TEXT PRIMARY KEY,
  imsi TEXT NOT NULL,
  first_seen_ms INTEGER NOT NULL,
  last_login_ms INTEGER NOT NULL
);

CREATE TABLE alarm (
  id INTEGER PRIMARY KEY,
  dev_id TEXT NOT NULL REFERENCES device(dev_id),
  event_no INTEGER NOT NULL CHECK(event_no>0),
  alarm_id TEXT NOT NULL,
  alarm_desc TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('open', 'cleared')),
  first_ms INTEGER NOT NULL,
  last_ms INTEGER NOT NULL,
  clear_ms INTEGER,
  UNIQUE(dev_id,event_no),
  CHECK ((status='open' AND clear_ms IS NULL)
      OR (status='cleared' AND clear_ms IS NOT NULL))
);
CREATE UNIQUE INDEX one_open_alarm
  ON alarm(dev_id, alarm_id, alarm_desc) WHERE status='open';

CREATE TABLE query_task (
  txn_no INTEGER PRIMARY KEY AUTOINCREMENT,
  dev_id TEXT NOT NULL REFERENCES device(dev_id),
  connection_id TEXT,
  status TEXT NOT NULL CHECK (status IN ('pending', 'success', 'timeout', 'link_lost')),
  reason TEXT,
  created_ms INTEGER NOT NULL,
  finished_ms INTEGER,
  response_json TEXT,
  CHECK ((status='pending' AND finished_ms IS NULL)
      OR (status<>'pending' AND finished_ms IS NOT NULL))
);
CREATE UNIQUE INDEX one_pending_query
  ON query_task(dev_id) WHERE status='pending';
```

response_json 为完整合法 911 JSON；其中 attrList 缺省和空数组可区分。业务对已用字段的校验在应用执行，SQLite 不要求额外 JSON 扩展。所有用户字段使用参数绑定，不拼 SQL。

M4落实时增加每设备event_no和UNIQUE(dev_id,event_no)，使恢复后的告警缓存可以匹配原事件；id仍为SQL全局主键。SQLite固定3.51.3随源码编译，设置application_id=BATT、user_version=1；实现和实测证据见第四步验收记录。

### 10.3 持久化成功与失败

| 数据/应答 | 第一版保证 |
| --- | --- |
| 110 / 111 成功 | 设备登记事务已提交；连接本身不持久化 |
| 310 / 311 成功 | 当前会话内属性已合法更新；不保证遥测历史或重启后属性仍在 |
| 410 / 411 成功 | 本帧告警集合的状态变化已提交 |
| query 返回已受理、911 成功状态 | 对应任务及结果已提交 |

不能把三种成功应答解释成相同持久化级别。关键业务采用“计算变更→事务提交→替换缓存→发送成功/展示终态”。SQL 失败执行 ROLLBACK、保留旧告警/任务缓存，不回成功，不发送尚未提交的 910。

磁盘满、持续 busy 或 I/O 错误超过预算时，记录 storage_error，停止受理新的关键业务并触发有期限的失败退出，退出码非零；不能只打印日志后继续宣称持久化正常。没有数据库可用性时也不继续接受一批无法确认的告警。

数据库提交与网络 ACK 无法组成单个原子事务。允许“提交成功但 ACK 丢失”；告警集合重发不得产生重复 open。第一版不保证跨重连、跨崩溃的所有上报 exactly-once。

### 10.4 启动恢复

启动时在事务中将历史 pending 全部改为 link_lost，reason=server_restart，填写 finished_ms；恢复失败则不开放监听。加载设备与 open 告警到相应分片，不恢复旧连接、不把旧属性标成新鲜，不重发历史查询。随后启动 I/O。

保留原数据库可保证已提交的查询编号继续增长。数据库备份、迁移须使用 SQLite backup API 或停服务并正确处理 WAL；不能在运行时只复制 access.db 后宣称完整备份。

## 11. 退出、失败和资源释放

SIGINT/SIGTERM 通过 signalfd 或仅做信号安全通知的处理器交给主循环；信号处理器不写 SQLite、不加普通 mutex、不调用复杂日志函数。

正常退出顺序：

1. 关闭监听，停止受理 CLI query 和新业务读取；保留 I/O 循环以发送工作线程返回结果。
2. 已进入工作队列的事件继续处理；尚留在接收缓冲中、未入队的字节不算已受理，记录数量，不承诺全部处理。
3. 工作线程在处理完已接纳事件后，将剩余 pending 查询提交为 link_lost/server_shutdown；退出阶段不再发新的 910。已接纳但尚未执行的查询命令，对已存在的设备档案记录 link_lost/server_shutdown 并返回编号；未知设备仍返回 not_found。
4. 主循环继续排空返回队列与 socket 发送缓冲，唤醒等待者；工作线程退出后各自在所属线程 finalize statement、关闭数据库连接。
5. 所有关键状态提交完成且待发字节清空后关连接并 join。正常 drain 期限默认 5 秒。超过期限，取消可中断等待、对 SQLite 执行 interrupt/回滚、记录未完成任务和未发字节，失败退出。

期限不是强杀线程的许可。第一版不承诺可以中断操作系统中的不可中断磁盘 I/O；自动测试驱动在额外宽限后可终止进程并判为退出失败。SIGKILL 不执行析构，崩溃测试只检查事务与启动恢复，不期待优雅退出。

退出后已持久化但未发出的 ACK 不回滚；重连后由终端重发以及服务幂等处理收敛。再次启动按第 10 节恢复。

## 12. 模拟器、数据与控制脚本

`batt-sim` 默认连接 127.0.0.1:19001，32 个独立终端 BT000—BT031。支持 `--devices`、`--report-interval-ms`、`--duration-sec`、`--seed`，并记录参数。默认每秒各发送一帧 310 与 410，是测试负载，不冒充原现场上报频率。

固定样例需独立核对字段、单位和预期状态；连续数值由可复现种子生成。服务和模拟器共享协议声明可以，共享同一业务状态机后相互验证不算独立证据。

控制口默认 127.0.0.1:19002，用有长度上限的换行文本命令；仅本地测试使用，定义为测试扩展，不宣称来自原终端协议。每条动作返回 action_id、执行确认和执行时间，测试不能靠随意 sleep 猜测动作已经发生。

| 动作 | 行为 |
| --- | --- |
| `slice BT000 1` | 下一对象每次最多 send 1 字节；仍正确处理短写，不保证服务端 recv 同样分片 |
| `glue BT000` | 下一个 310 与 410 串接后提交发送；接收边界由 TCP 决定 |
| `badjson-balanced BT000` | 发送已配平但语法非法对象，随后好对象 |
| `badjson-unclosed BT000` | 发送未闭合对象/字符串，随后可继续字节；预期超过期限关闭，不承诺恢复 |
| `alarm BT003 03 1` | 将03加入该终端活跃集合并发完整410 |
| `alarm BT003 03 0` | 从集合移除03；若集合空则发000/0，否则发剩余活跃项 |
| `slow911 BT005 5000` | 对收到的910延迟5秒，原样回显其txnNo；不阻塞其他模拟终端 |
| `duplicate911 BT005` | 对下一查询生成重复响应 |
| `relogin BT007` | 保留旧连接，另建同devId的新连接并登录；保留连接标签便于注入旧消息 |
| `stall BT009` | 停止310，连接保持且可继续410 |
| `slowread BT011` | 暂停读取服务下发内容，测试发送积压 |
| `disconnect BT013` | 关闭指定终端连接，按脚本选择是否重连 |

让某个工作线程任务 sleep 200 ms、让 SQL 返回错误、强制 fd 数字复用等动作放在显式测试钩子中，默认构建不启用；不能把人为慢业务称为真实慢终端。

## 13. 自动化测试与验收

解析单测直接喂字节，不用 send 次数推断 recv 次数。状态机和截止点单测使用可控时钟；端到端测试使用真实单调时钟、明确屏障和较宽裕窗口。数据库事务样例用临时库，不接企业平台。

| 测试 | 必须断言 |
| --- | --- |
| 所有单切分位置、单字节、随机多切分 | 相同对象序列与字段；无重复、无漏帧 |
| 连续对象、字符串括号、转义引号与反斜杠 | 分界正确，切分状态跨片段保持 |
| 配平坏JSON后正常对象 | bad_json加一；后续对象生效 |
| 不配平对象/未闭合字符串 | 期限或容量到达后关闭，服务不挂起，不误认恢复 |
| 已闭合超大对象、深度超过64、长残帧 | 分别触发上限；内存不越界 |
| 未使用字段含浮点/布尔/null | 报文仍可处理；已用字段类型错误整帧拒绝 |
| 未登录上报、连接伪报其他devId、无效新登录 | 不更新业务；无效登录不替换合法旧会话 |
| 重复登录与fd复用 | 新connection_id生效；旧任务/关闭通知/发送命令不影响新连接 |
| 部分属性与过期 | 缺字段为no_data；只更新SOC不能刷新旧温度；超过90秒为stale |
| 告警持续、减少、全清、恢复再触发 | 持续仅一个open；一项消失但另一项仍在时只清前者；000清空；再次触发新事件 |
| 告警组缺席、矛盾000、未知描述 | 缺席不推断恢复；矛盾帧不提交部分结果；未知项按契约忽略 |
| 查询正常与空结果 | txnNo/连接匹配；success及response_json持久化；缺省attrList可区分 |
| 超时边界 | 2.9秒已入队但3.2秒处理可成功；3.1秒入队超时；精确等于截止点为超时 |
| 迟到、重复、旧连接911 | 终态不反转，late/duplicate/orphan各自计数符合定义 |
| 查询并发与替换 | 同设备第二任务拒绝；旧pending为link_lost/replaced；新会话不能完成旧任务 |
| 背压高低水位 | 暂停读但发送/错误事件仍推进；低水位后缓存先入队；全局与每级缓冲均有界 |
| 短写、EAGAIN、慢接收端 | 字节不丢不重复，发送队列有界，超限/超时关闭具体连接 |
| 慢任务隔离 | 同分片与另一分片都测，报告各自延迟；不声称同分片完全隔离 |
| 数据库失败/锁竞争 | 不成功ACK、不更新关键缓存、不发未提交910；超预算失败退出 |
| 崩溃恢复 | 已提交open保留；pending改为link_lost；未提交事务无部分行；不恢复在线 |
| 编号持久性 | 重启及删除部分历史行后，新已提交查询编号不复用旧已提交编号 |
| 正常退出与退出超时 | 已受理关键任务原子提交；剩余pending有明确结果；超过期限有非零退出及未完成统计 |
| 墙上时钟跳变 | 单调时钟驱动的超时和数据年龄不受影响 |

测试数据库 UNIQUE/CHECK 约束，至少包括重复 open、同设备双 pending 和终态条件更新。ASan/UBSan 与线程检测分别运行；先修正已发现缺陷，再做负载比较。

必须保留两类证据：原代码对应的固定报文样例，以及人为设计且有预期断言的边界样例。没有硬件时，明确标注“协议子集与模拟终端验证”，不写“已验证全量企业协议”。

## 14. 负载、指标与报告

32终端是默认演示，不是硬编码规模。阶梯测试可从32、128、512终端开始，具体上限受机器和配置约束；均为计划测试点，不是实现前的性能承诺。保持单终端频率不变，再单独测试提高频率，区分连接规模与报文吞吐。

记录 CPU/内存、实际连接数、有效报文速率、各队列长度与字节高水位、admitted到业务完成的p50/p95/p99、暂停读累计时间、发送积压、数据库提交延迟、查询成功/超时率和恢复耗时。解析/排队/数据库延迟尽可能分开。

1工作线程与2工作线程比较使用相同设备集合、频率、种子、时长、SQLite设置和机器。分别测试正常、慢任务、慢数据库；报告同分片及另一分片，记录哈希分布。全局写锁导致数据库负载无法受益也是有效结论，不隐去。

至少进行一次持续30分钟的稳定负载测试和一次有界过载/恢复测试；这些是验收目标。测试硬件、Linux/WSL版本、编译选项、依赖版本和脚本必须可追溯。短时间模拟连接数不能证明现场长期稳定。
