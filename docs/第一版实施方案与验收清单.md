# 第一版实施方案与验收清单

> 版本：V1 / 1.0.0最终验收。进度：A01—A06、B01—B05、C01—C06、D01—D07、F01—F06均已在现有Ubuntu完成并验收。详见[第一步](第一步验收记录.md)、[第二步](第二步验收记录.md)、[第三步](第三步验收记录.md)、[第四步](第四步验收记录.md)、[最终验收记录](最终验收记录.md)。
> 项目：电池终端接入与运维服务（batt-access）。学习主线：Linux/C++ 系统与网络编程，兼顾服务端开发。
> 本文定义第一版交付范围。完整规格保留为设计参考；本文明确列出的降级与取舍优先，不能要求第一版同时满足完整规格的全部增强项。

## 1. 第一版完成后，能演示什么

一组模拟电池终端连接 Linux 服务端，发送登录、属性与当前告警集合。服务维护设备及新鲜度，合并告警，接受只读参数查询；重复登录不串会话，查询迟到不改变终态，已确认的告警和查询记录可以在进程重启后恢复。

终端数据由模拟器和独立固定样例生成。第一版不要求真实电池硬件，不接企业生产系统，不将模拟结果写成现场验证。

核心交付两个可执行程序 `batt-access`、`batt-sim`，另带 `batt-db` 本地SQLite检查工具，以及测试与演示记录。测试脚本负责重启服务，不开发 supervisor。

## 2. 范围冻结与相对完整规格的取舍

| 项目 | 第一版决定 | 对完整规格的影响 |
| --- | --- | --- |
| 技术栈 | C++17、Linux/WSL、epoll LT、成熟JSON库、标准库线程、有界队列、SQLite C API | 保留服务端主线 |
| 工作线程 | 两个固定分片工作线程；支持用一个线程做对照 | 不写通用任务框架，不做运行时扩缩容 |
| 连接规模 | 模拟器默认32；服务默认最多128条活跃或等待关闭通知的连接，参数可调 | 不强制512终端或大规模性能结论 |
| 查询超时 | pending准备提交前记录单调时钟起点，截止3秒；按工作线程处理响应时刻判定 | 替代完整规格第9节“按入队时间合并截止点”的严格语义，见第6节 |
| 唤醒及信号 | I/O循环最多等待50ms，每轮收取工作结果、检查连接期限与停止标记；工作线程用条件变量 | eventfd/signalfd不是首版必需依赖；处理器只做信号安全通知 |
| 队列满 | 关闭当前无法入队的连接，计overloaded；保留已受理任务及有界关闭通知 | 第一版采用断开式负载卸载，不实现完整规格第7节的MOD高低水位暂停/恢复 |
| 缓冲上限 | 连接数、对象大小、收发缓冲、事件队列和返回队列全部有限 | 不做全服务128MiB精细记账 |
| 压测 | 32终端功能演示；1与2个工作线程做同/异分片慢任务对照 | 不以30分钟、p50/p95/p99、阶梯扩容作为首版交付门槛 |
| 退出 | 停止受理、完成已接纳关键任务、结束pending并有限排空发送；超时失败退出 | 不建设通用关闭框架；边界仍需明确 |
| 后续选项 | HTTP、MySQL、Redis、MQTT、通用线程池、性能优化 | 不在首版实现，不作为职业方向限制 |

这份取舍允许把项目先做出来，但不能删去 connection_id、单调计时、完整发送、基本容量限制、关闭通知和数据库事务规则。

## 3. 所有阶段保持一致的基本规则

### 3.1 协议

- 使用原电柜TCP协议的连续JSON对象，不解析105/141字节串口帧。
- 支持110/111登录、310/311属性、410/411告警、910/911保护参数查询。
- 用成熟JSON库解析全部合法值类型，再校验业务字段；未知经纬度等浮点字段可被忽略，不能导致整帧误拒绝。
- 切分器处理字符串、转义引号、连续反斜杠和跨recv残帧。已配平语法错误可丢弃该对象；未闭合对象或字符串超时则断开，不承诺任意坏流都能重同步。
- 属性使用四个id：01111001总电压/100、01112001电流/100、01113001 SOC、01119001电芯温度；已用字段非法或重复则整帧拒绝。
- 告警采用原周期上报路径的“当前集合”模式，id=01003001，已用desc为01、03、06；000/0表示该组全恢复。组缺席不推断恢复，000与活跃项冲突则整帧拒绝。
- 同一组内一项消失、另一项仍活跃时，只恢复消失的一项。单项恢复命令是模拟器更新集合的便利入口，发送时仍用完整集合。

### 3.2 会话、顺序与关闭

- 每次accept分配独立connection_id；fd只用于系统调用。任务、结果和断开通知都带connection_id。
- 登录成功前不处理310/410/911；同连接冒用其他devId不更新状态。合法新连接才替换旧连接，无效登录不能踢掉旧连接。
- 同一devId固定进同一队列。最终I/O线程独占fd及收发缓冲；所属工作线程独占设备业务、告警、任务和数据库连接。不共享无锁业务map。
- I/O负责收发与路由所需的基础JSON解析，工作线程负责业务。工作线程不直接send。
- I/O关闭后必须通知所属工作线程，工作线程只对匹配的当前connection_id结束会话。断开通知队列满时，每连接至多保留一条待投递通知，内存受连接总数上限约束；不得阻塞I/O或静默丢失通知。
- 新连接生效后再处理的旧任务、旧结果、旧关闭通知，不能更新或关闭新会话。替换之前已完成的合法旧任务不追溯撤销。

### 3.3 新鲜度与时钟

运行期限和年龄用steady_clock；数据库时间使用UTC Unix毫秒。四个属性分别保留更新时间；缺字段为connected_no_data，最老字段超过90秒为connected_stale，四项齐全且未过期为online_fresh，无连接为offline。

只更新SOC不能刷新旧温度。重连不把旧快照继承为新连接的新鲜数据。查询第一版只对online_fresh执行。

## 4. 四步实施与每步验收

每步结束先运行其测试，记录结果，再进入下一步。禁止先搭满全部目录、框架和压测工具再验证第一条登录。

### 第一步：单设备协议闭环

实现CMake最小构建、JSON切分器、单连接epoll LT收发、内存设备状态、属性和告警集合，以及单终端模拟器。此阶段没有数据库、工作线程、查询和多连接业务。

第一次写send就维护发送偏移，处理短写、EINTR、EAGAIN和SIGPIPE；不用“先假定一次发完”。I/O先拥有全部状态，第三步再显式转移业务状态所有权。

**本步通过条件：**

- [x] A01：固定110、310、410样例可解析，字段和单位与手工预期一致；只登录一次，返回关联正确的111/311/411。
- [x] A02：直接向切分器喂单字节、全部单切分位置和两个连续对象，输出对象不重不漏。
- [x] A03：字符串括号及转义不破坏边界；配平坏JSON后好对象可继续；不配平对象在5秒或容量上限后关闭。
- [x] A04：非法SOC、缺路由字段、未知浮点字段、未登录上报，分别符合拒绝/忽略规则，不产生部分属性更新。
- [x] A05：告警持续不重复open；移除一项只清该项；000清空；恢复后再触发形成新事件。
- [x] A06：发送被人为限制为小块仍能拼回完整JSON；临时不可写后可继续，发送缓冲不无限增长。

验收证据：一组解析单测、一段单设备收发日志、告警集合变化的断言结果。此阶段ACK仅表示内存处理成功，不能据此宣称持久化完成。

### 第二步：连接身份与多设备

将模拟器扩展为默认32终端，引入connection_id和多连接注册表，处理重复登录及新旧连接交错。仍可先在单I/O线程处理业务，减少同时引入的变量。

**本步通过条件：**

- [x] B01：32个模拟终端各自登录、更新属性，设备状态和告警互不串写。
- [x] B02：同devId的新连接合法登录后替换旧连接；无效新登录不影响旧会话。
- [x] B03：旧连接报文、旧发送结果及旧关闭事件不影响新会话；通过测试钩子或单测构造相同fd数字、不同connection_id验证。
- [x] B04：登录后伪报其他devId被拒绝；重复同连接登录不重置正在运行的会话。
- [x] B05：停止310但继续410，设备从fresh转stale；部分属性更新不能刷新整份快照。

验收证据：32设备状态输出、重复登录及fd复用测试、可控时钟的新鲜度测试。

### 第三步：两个分片工作线程与查询

把设备业务状态从I/O移动到所属工作线程，新增有界输入/返回队列、条件变量和只读运维CLI。支持query、status、devices、task、stats、quit，结果仍由I/O输出。无SQLite时可使用内存编号和任务表，只验证本次运行内的逻辑；不得跨重启比较编号。

I/O循环以最多50ms等待收取工作结果，不能等待队列空位。工作线程定时醒来检查查询期限，或用条件变量的有期限等待；不要求实现完整规格的入队时间排序算法。

**本步通过条件：**

- [x] C01：同devId严格顺序执行；能证明设备落在哪个分片；无工作线程直接send或跨线程读取普通业务map。
- [x] C02：query正常success、超过3秒timeout、断线/relogin为link_lost；同设备第二个pending拒绝。
- [x] C03：迟到、重复和旧connection_id的911不改变终态；计数类别明确。
- [x] C04：工作队列/返回队列有界；入队失败执行断开式负载卸载，I/O不阻塞，关闭通知不丢，其他连接仍能推进。
- [x] C05：1与2个工作线程运行相同慢任务场景，分别记录同分片与另一分片延迟；允许没有收益，不宣称写库并行。
- [x] C06：SIGTERM唤醒等待者，处理已接纳任务、关闭连接并join；没有卡在队列条件变量上的线程。

验收证据：查询四状态及终态测试、满队列测试、1/2线程对照表和正常退出测试。人为慢任务由测试钩子注入，不称为真实设备慢响应。

### 第四步：SQLite与重启恢复

采用完整规格的表结构及约束，查询编号替换为数据库AUTOINCREMENT。每工作线程各自使用连接和statement，写事务受公共有期限锁约束；不在运行中的I/O循环调用SQLite。启动先初始化和恢复，再开放监听。

**本步通过条件：**

- [x] D01：告警一帧的全部变化原子提交，提交后替换缓存并回411；一个键至多一条open。
- [x] D02：pending先提交再发送910；成功911的完整response_json和任务终态一起提交；同设备至多一个pending。
- [x] D03：写库失败不回关键成功ACK、不改告警/任务关键缓存、不发送未提交910；有限重试失败后停止受理并以非零码退出。
- [x] D04：重启保留open告警；pending变link_lost/server_restart；设备不会凭历史记录恢复在线或新鲜。
- [x] D05：重启后以及删除部分历史行后，新的已提交query编号不复用旧编号；未知设备query返回not_found。
- [x] D06：在事务提交前、提交后未回ACK等位置注入崩溃，数据库不出现半个告警事务；重发集合不产生重复open。
- [x] D07：正常停止结束剩余pending；数据库失败或超过退出期限有明确非零结果和未完成统计；不承诺SIGKILL执行析构。

验收证据：临时SQLite库的约束/恢复测试、故障注入日志、正常与异常重启前后查询结果。这里通过后，才允许宣称具备持久化和重启恢复能力。

## 5. 第一版资源限制与最小过载策略

| 资源 | 默认限制 | 到达上限的动作 |
| --- | --- | --- |
| 活跃或等待交付关闭通知的连接 | 128 | 拒绝新连接，不能无限保留待关闭记录 |
| 单JSON对象 | 64KiB | 关闭对应连接；已闭合大对象也检查 |
| 未闭合对象 / 未完成登录 | 5秒 | 关闭对应连接 |
| JSON深度 | 64 | 解析时限制，拒绝过深对象 |
| 每连接接收缓冲 | 256KiB | 关闭对应连接 |
| 每连接发送缓冲 | 256KiB | 关闭对应连接 |
| 每分片输入队列 | 64事件；单事件原始报文不超过64KiB | 当前待入队连接overloaded关闭，已有事件不丢 |
| 返回队列 | 合计128命令；原始业务对象不超过64KiB，另有有界状态/路由元数据 | 工作线程可中断等待，I/O继续取结果；等待不持数据库锁 |
| 发送无进展 | 5秒 | 关闭连接，关联pending按规则结束 |

帧载荷需有明确所有权，不能一边把原始报文放队列，一边无界保存每次解析副本。对已读的一批字节逐个切分、尝试入队，不先构造任意长的对象列表。

第一版到队列满时明确断开，属于负载卸载，不承诺无损背压。如果以后实现暂停/恢复，使用MOD调整EPOLLIN并保留必要事件；DEL用于真正移除/关闭连接。

## 6. 第一版查询时间与持久化语义

为了减少截止点合并逻辑，第一版冻结为以下规则，不再保留完整规格的严格入队时间承诺：

1. query命令被工作线程处理后，检查设备fresh且无pending，再记录steady_clock起点t0。最终版本先提交pending，再向发送队列投递910；deadline=t0+3秒，包括数据库提交、返回队列和发送等待，不包括此前CLI命令排队时间。
2. 工作线程处理911时先检查当前单调时间，`now >= deadline`则先把pending结束为timeout，当前911按迟到处理；`now < deadline`且编号/会话匹配才允许成功。检查通过后的数据库提交耗时不追溯改变这次资格判定。
3. 所有任务转换仅在所属工作线程串行进行；定时检查也在该线程执行，不让I/O直接修改timeout。成功或其他终态提交后不能被后续事件覆盖。
4. 数据已经到达或入队，但业务队列处理太晚，也可能超时。这是第一版的已知取舍，演示和README必须说明；不再要求“2.9秒入队、3.2秒处理仍成功”。
5. I/O收到过期且未开始发送的查询命令不再发送。若查询JSON已经发出部分字节后到期，关闭该连接，不截断对象后继续发下一对象。重复关闭事件仍按connection_id去重。
6. 不在线/过期设备已有档案时记录link_lost及reason，不发910；未知设备直接not_found。拒绝busy、存储失败未受理，都不能伪造成功任务。

数据库失败后的ACK和内存一致性按完整规格保留：110登记提交后111成功；310的311只确认内存接纳；410提交后411成功；任务状态和结果提交后CLI才展示为成功。不能统一声称所有ACK都代表数据已落盘。

## 7. 首版退出的最小要求

收到停止信号后停止accept、新query和新业务读取，I/O继续消费返回结果并发送。队列内已接纳的属性/告警继续处理；不再新发910，未执行查询及现有pending按server_shutdown结束。

随后工作线程在自己的线程内关闭statement和数据库，I/O有限排空发送，关闭fd并join。默认退出预算5秒；超预算记录未完成任务/未发字节并非零退出。所有条件变量等待都必须能被停止状态唤醒。

未入队的接收缓冲不算已受理，停止时可以丢弃并计数。数据库提交但ACK未发出不回滚；重连重发依靠集合幂等收敛。不可中断的系统I/O不承诺硬时限，测试驱动可在额外宽限后终止并判失败。

## 8. 最小模拟器和演示入口

模拟器默认32终端，devId为BT000起，使用固定样例或按设备编号确定的数值；实现命令行脚本入口即可，第一版不要求另开19002控制服务器。每个脚本动作都输出执行完成标记，测试用标记或屏障同步，避免靠猜测sleep时间验收。

至少支持：单终端/32终端启动、单字节切片、连续对象、配平坏JSON、不配平残帧、登录替换、停止属性、告警集合增加/减少/清空、910延迟或不回应、主动断开。

延迟911使用模拟器调度，不睡住所有模拟终端。切片send不能保证接收recv也按同样边界，确定性切分仍由直接喂字节单测证明。

最终演示固定为：

1. 启动服务及32终端，显示设备fresh和计数。
2. 一台设备持续过温，只保留一条open；恢复后再次触发得到新事件。
3. 一台设备停属性，显示stale；另一台同devId新登录，旧任务/数据不能串会话。
4. 查询一次正常、一次迟到，分别success和timeout；迟到不翻案。
5. 存在open和pending时杀掉服务，重启后检查open保留、pending为link_lost，再由终端重新登录采集。

数据来自模拟，不预填并发吞吐、恢复耗时或企业上线成果。

## 10. 第一版之后再决定的增强

按实际瓶颈选择：MOD高低水位无损暂停/恢复、eventfd唤醒、严格按接纳时间判定查询、全局字节预算、更多连接和频率阶梯、p50/p95/p99、30分钟或更长运行、更多业务接口与存储方案。

不因“服务端项目就必须有”而加入Redis/RPC等；也不因“来自嵌入式实习”而排除后续服务端扩展。

面试首先讲清三件事：为何连接编号不能只用fd；同设备如何保持顺序且慢任务影响谁；告警/查询提交、超时和重启时能保证什么。完整规格里的更多问题保留为深入复习，不作为开工门槛。
