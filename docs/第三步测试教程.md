# 第三步测试教程：分片工作线程与参数查询

> 0.3.1交互修复：终端默认安静模式，也可加--quiet。自动上报不再刷屏，命令结果以中文单独显示；输入quiet off恢复详细JSON。

本轮对应C01—C06。继续使用同一台Ubuntu和MobaXterm，源码及Linux路径不变。数据库仍未实现，任务和结果只在当前进程内保存。

## 1. 先退出旧服务，再运行自动测试

如果上一步的batt-access仍在终端A运行，先按Ctrl+C退出。已运行的旧进程不会因为源码更新而自动变成新版。

在Ubuntu SSH终端执行：

```sh
cd /home/book/batt-access
sh scripts/test-linux.sh
```

本轮增加pthread链接和两个测试目标，第一次会重新编译，耐心等待最终结果。成功应显示4/4个CTest测试组通过：

| 测试组 | 内容 |
| --- | --- |
| core | 原有402个断言，回归协议与会话 |
| query_unit | 31个断言，查询状态、截止点、队列关闭唤醒、部分发送期限 |
| network | 原有19个真实TCP场景回归 |
| query_network | 17个场景，含CLI、查询、线程协作及控制台可读性 |

合计433个核心断言、36个网络场景。运行时间约18秒，随机器负载变化，不把耗时当性能验收门槛。

## 2. 在两个终端里看一次成功查询

终端A启动服务：

```sh
cd /home/book/batt-access
./build/batt-access --workers 2 --quiet
```

ready应包含milestone=3、workers=2、cli=true、query_timeout_ms=3000。此时服务占用该终端，后面介绍的query/status等命令直接输入到这个正在运行的程序里，不是在新的Linux shell中执行。

终端B启动持续模拟终端：

```sh
cd /home/book/batt-access
./build/batt-sim --demo serve --devices 1
```

等待B显示serving。它每秒持续上报属性和告警，并监听服务下发的910参数查询；不像普通演示那样几秒后退出。

回到A，在服务运行时输入以下命令，每行按回车：

```text
status BT000
query BT000
```

预期：

1. status输出[STATUS]，显示online_fresh（在线，数据新鲜）、电压、电流、SOC、温度和worker。
2. query先显示[QUERY #编号] pending（等待终端应答）。
3. B显示query_response，回显相同txnNo。
4. A随后显示[QUERY #编号] success（查询成功），下一行[RESULT #编号]显示参数，样例protect=4150。

查看结果时，在A输入：

```text
task 1
```

1只是第一次查询的例子，请换成实际日志里的txnNo。任务编号在本次服务运行内全局唯一，重启暂时会从头分配；第四步接入数据库才解决跨重启编号。

## 3. 演示超时与迟到应答

保持A的服务运行，在B按Ctrl+C结束模拟器，然后重新启动：

```sh
cd /home/book/batt-access
./build/batt-sim --demo serve --devices 1 --query-delay-ms 5000
```

等B显示serving后，在A输入：

```text
query BT000
```

本次B延迟5秒才回应，而服务的默认查询期限为3秒：

- 先出现pending。
- 约3秒后出现timeout。
- 约5秒后B发出911，A记录late_response；任务不会改回success。
- 用task加实际编号查询，状态仍为timeout。

第一版按工作线程处理911时的单调时间判断期限。即使数据早已到达，但因为队列拥堵处理太晚，也可能超时；当前不提供按网络到达时间或入队时间追认成功的保证。

若想看“同设备只能一个pending”，在上述慢应答模拟器运行时，将下面两行一起粘贴到A：

```text
query BT000
query BT000
```

第一条受理，第二条query_rejected，reason=busy。第一条结束后才能再次查询。

## 4. 演示断线与任务状态

慢应答模拟器仍在运行时，在A发起query；看到pending后，在3秒内到B按Ctrl+C断开连接。A应记录link_lost，原因peer_eof，而不是继续等一条永远不会来的响应。

如果操作超过3秒，先变成timeout也符合规则。自动测试使用屏障和明确时间点验证断线与替换，不依赖手速。

在设备offline时query会记录link_lost/offline并且不下发；从未登记过的设备返回query_rejected/not_found。重新登录必须重新采集属性，才会online_fresh。

## 5. 可以使用的命令

下面都是运行中服务端A的命令，命令行支持多次输入：

| 命令 | 用途 |
| --- | --- |
| help | 显示命令 |
| devices | 按分片输出设备快照，每个worker输出完成标记 |
| status BT000 | 当前状态及所属worker |
| query BT000 | 发起只读保护参数查询 |
| task 实际编号 | 查看本进程内的任务及响应 |
| alarms BT000 | 查看内存告警事件 |
| stats | 输出I/O队列/过载统计和各worker查询统计 |
| quit | 请求排空已受理工作并退出，效果类似Ctrl+C |

不同设备、不同worker的日志可能交错，这是正常的；同设备业务仍按同一条队列顺序处理。pending只表示服务器已建立内存任务并准备发送，不证明终端已收到。

## 6. 观察1个与2个工作线程的区别

在任意另一个Ubuntu SSH终端执行：

```sh
cd /home/book/batt-access
python3 scripts/compare-workers.py
```

脚本使用临时业务端口，自动运行1个worker和2个worker两种配置，对BT000业务处理注入300ms延迟，再同时测BT001、BT002的应答时间。

- 两个worker时，BT000与BT002在同一分片，BT001在另一分片。
- 单worker时三者都排队。
- 输出WORKER_COMPARISON包含两组实际毫秒值，结果随调度变化，不要求固定数值或固定提升比例。

本轮Debug样本：单worker的BT001约326.63ms、BT002约326.36ms；两个worker的BT001约0.94ms、BT002约294.53ms。这说明另一个分片可继续工作，同分片仍会受慢任务影响。它不是数据库并行写性能，也不是高并发吞吐结论。

## 7. 本轮架构要看懂什么

```text
I/O主线程：accept / recv / 切JSON / 基础解析 / send / CLI
       │ 按devId的稳定哈希分片
       ├─ 有界队列0 → 工作线程0：本分片设备、告警、查询、超时
       └─ 有界队列1 → 工作线程1：本分片设备、告警、查询、超时
工作线程 → 有界返回队列 → I/O主线程发送应答
```

- socket与连接缓冲只由I/O操作，业务map只由所属worker操作。
- 同设备始终进同一队列，保持顺序；当前是固定分片执行模型，没有通用任务调度框架。
- I/O等待最多10ms后检查工作结果，满足第一版“最多50ms”的范围；没有eventfd依赖。
- 输入队列满时断开当前连接并计overloaded，I/O不等队列空位。每连接至多保留一条待投递关闭通知，不能丢失该通知。
- 旧连接的晚到工作结果以token查表，不能按已复用的fd发送到新设备。
- 新登录已经生效后，旧连接排队中的重复110也不能抢回会话；这是本轮专门增加的并发测试。

当前输入队列每分片64条、返回队列合计128条。默认两个worker，每分片最多512个设备档案、1024条内存查询任务；满时明确拒绝，第四步再由数据库承担持久化历史。

## 8. 内存和线程检查

0.3.0基础版本已运行检测构建并保留记录；0.3.1显示改动已做普通完整回归。你可以在普通测试通过后自行复现检测构建，使用不同目录：

```sh
cd /home/book/batt-access
BATT_BUILD_DIR=build-asan BATT_SANITIZE=ON sh scripts/test-linux.sh
BATT_BUILD_DIR=build-tsan BATT_THREAD_SANITIZE=ON sh scripts/test-linux.sh
```

ASan/UBSan检查内存和未定义行为，TSan检查被执行场景中的线程竞争，不能同时放进一个构建。每个构建都应4/4通过。首次检测构建会比普通构建慢。

独立运行时：

```sh
./build/query_test
python3 tests/query_network_test.py ./build/batt-access ./build/batt-sim
```

应分别显示31 checks passed，以及Ran 17 tests和OK。

## 9. 边界和下一步

本轮没有SQLite，所有ACK仍是内存级确认，任务和编号不能跨进程重启恢复。关闭时会完成已受理工作、结束pending并有限排空发送；还没入队的接收数据不保证处理。5秒退出预算超限会失败退出，不能称为无条件无损关闭。

`--demo normal`和`--demo relogin`仍可回归上一步演示；交互查询请用持续运行的`--demo serve`。如果把query输入到shell而显示command not found，说明输入错终端了。

完成成功查询、延迟超时与自动测试后，可反馈“第三步已复现”。下一步才接SQLite，实现告警和查询的事务提交、编号跨重启及启动恢复。详细证据见[第三步验收记录](第三步验收记录.md)。
